# WannaSong 하네스 운용

이 저장소의 **지침·문서·검사기를 쓰고 고칠 때**의 규칙. 기능 코드 규칙은 `wannasong-architecture`·`wannasong-conventions`·`wannasong-contract`를 따른다.

배경: 현 세대 모델은 스스로 판단·검증·완결한다. 촘촘한 금지 나열·일괄 검증·일괄 위임은 토큰만 늘리고 품질은 그대로다. 그래서 규칙을 **금지 나열**이 아니라 **판단 기준**으로 쓴다. 이 하네스는 afin-ios 하네스(대원칙)를 이식한 것이며, "스택·워크스페이스가 바뀔 수 있다"는 전제와 그것을 기계로 잡는 검사기가 추가됐다(`CLAUDE.md` §8).

## 규칙은 판단형으로 쓴다

- **새로 추가하는 규칙**(CLAUDE.md 항목, 스킬 문구, 자동메모리)은 "언제 적용하고 언제 적용하지 않는지"를 같이 적는다. 조건 없는 "항상/반드시/무조건"은 쓰지 않고, 예외를 둘 거면 예외를 규칙 안에 쓴다.
- 규칙에는 **왜**(어떤 실제 사고에서 나왔는지)를 한 줄 남긴다. 근거 없는 금지는 나중에 판단할 수 없다.
- 기존 규칙은 실제로 충돌·오작동이 확인됐을 때만 손댄다. 일괄 재작성하지 않는다.
- **예외 — 도메인 하드 제약은 조건 없이 쓴다**: 스택 사실은 `wannasong-stack` 한 곳 / 계약 변경은 다섯 곳 동시(`wannasong-contract`) / 권한·상태의 진실은 실시간 서버 / 설정은 환경변수만 / 런타임 동작 검증("빌드 통과"≠"검증") / `.env.local`·`.omc/` 커밋 금지. 이들은 판단형으로 완화하지 않는다.

## 스택 가변성 원칙

- 스택 이름·명령·버전은 **`wannasong-stack`에만** 쓴다. 다른 문서는 "실행 명령은 `wannasong-stack` 참조"처럼 가리킨다. 드리프트 표면을 한 곳으로 모아야 훅이 잡을 수 있다.
- 부득이 다른 문서에 스택·코드 사실을 쓸 때는 **백틱으로 감싼다** — 검사기의 stale 참조 검사는 백틱 토큰만 본다. 존재하지 않는 가상의 경로·심볼(계획 중인 apps 아래 api 디렉터리, Java 함수명 등)을 예시로 들 때는 **백틱을 쓰지 않는다**(오탐 방지). 검사기가 실제 오탐을 내면 문서를 비틀지 말고 `stack-manifest.json`의 `refIgnore`에 토큰을 넣는다.
- 규칙이 특정 스택에 묶여 있으면(예: "`transpilePackages`로 계약을 소스 소비") 그 문장에 어떤 스택 사실에 의존하는지 드러나게 쓴다. 스택이 바뀔 때 `wannasong-harness-sync`가 그 문장을 grep으로 찾아 고칠 수 있어야 한다.
- 워크스페이스가 늘면 스킬을 늘리기보다 **기존 스킬에 절을 추가**하는 것을 먼저 검토한다. 스킬이 늘수록 레지스트리·description 중첩 관리 비용이 는다. 새 스킬은 트리거가 명확히 분리될 때만(예: 실시간 서버 코드가 들어와 도메인 로직 규칙이 웹과 다를 때).

## 검사기를 고칠 때

- `.claude/harness/harness-check.mjs`는 **node 내장 모듈만** 쓴다(node_modules 없이 훅이 돌아야 한다). 의존성을 넣지 않는다.
- 판정 로직·목록(`NODE_FRAMEWORKS`·`POLYGLOT_MARKERS`·`DEPLOY_FILES`·`WATCH`·`HIGH_LEAF`)을 바꿨으면 `--selftest`를 돌려 결함 주입 케이스가 전부 PASS인지 증거로 남긴다. 새 종류의 결함을 잡게 했으면 그 케이스를 `--selftest`에 추가한다 — 검사기의 검증 내용도 하네스와 함께 자란다.
- 오탐을 고칠 때는 규칙을 좁히는 쪽(토큰 분류 추가)으로 하고, 검사 자체를 끄지 않는다.
- 훅 출력은 짧게. 같은 결과를 반복 주입하지 않는 억제 로직(`.omc/state/harness-check-last.json`)을 깨지 않는다.

## 사고 강도(effort)

- 기본은 **low~medium**. 파일 몇 개 읽고 판단이 서는 일에 최대 강도를 쓰지 않는다.
- 올리는 경우: 원인이 불명확한 상태 불일치·재생 끊김 버그, 계약(이벤트·KV 스키마) 변경, 스택·워크스페이스 교체, 되돌리기 어려운 삭제, 상대 저장소 배포 순서가 얽힌 판단.
- 올렸으면 **왜 올렸는지 한 줄**로 밝힌다.

## 리뷰 보고

- 찾은 것은 **전량 보고**하고, 사용자가 보는 요약은 **심각도로 필터**한다(기본 HIGH 이상). LOW/INFO는 목록만 남기거나 접어 둔다.
- 확신이 없다고 빼지 않고 **확신도**(확실 / 추정 / 미확인)를 적는다.
- 각 지적에 **근거 출처**(스킬·규칙·`파일:라인`)와 **심각도**(CRITICAL / HIGH / MEDIUM / LOW / INFO)를 붙인다.
- 리뷰를 서브에이전트에 위임할 때 이 규율을 프롬프트에 그대로 명시한다.

## 문서 분량

- 상한은 **계획·스펙 15KB, 리포트·요약·리뷰 6KB**(KB=1,024B). `CLAUDE.md`도 15KB — 넘으면 세부를 스킬로 내린다(검사기가 경고).
- 넘길 이유가 있으면 문서 안에 그 예외와 **초과분의 근거**를 적고 넘긴다.
- **채우기 섹션 금지.** 쓸 내용이 없는 섹션(빈 "리스크"·"향후 과제", 항목 없는 표)은 만들지 않는다.
- 완료된 계획·리포트는 `tasks/archive/`로 옮긴다(`git mv`로 이력 보존). `tasks/plan-nextjs-migration.md`는 마이그레이션이 끝나면 아카이브 대상.

## 검증·위임 강도

프로젝트 `CLAUDE.md` §2·§4가 단일 진실 소스다. 요지: 위임은 크고 독립적이며 병렬 가능한 작업에만, 자기 결과 확인용 위임 금지, 동시 스폰 낮게. 별도 리뷰 lane은 리스크가 크거나 판단이 갈릴 때만. 완화되지 않는 것: 빌드 통과≠검증, 실제 호출 안 한 워크플로우 이름 금지, 자동 확인 불가(브라우저 렌더·실제 재생·Java 없는 소켓 경로)는 "확인 불가 — 육안 필요"로 정직하게, 검증 주장에는 증거.

## 자기 상태를 잘못 단정하지 않기

- 파일 상태가 예상과 다르면 "내 편집이 지웠다"고 단정하기 전에 `git diff`로 HEAD 대비 확인한다. 협업자의 동시 편집일 수 있다(afin 하네스에서 실제 오보고 사례).
- 자동메모리·lessons가 코드와 충돌하면 메모리를 사실로 주입하지 말고 **코드로 먼저 검증**한다(afin에서 stale 메모리를 서브에이전트에 주입한 사고).
- 서브에이전트 결과가 얇으면 사용자에게 불평하지 않고 직접 확인해 답을 만든다.
